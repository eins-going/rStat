# 물류기기 공동이용 통합 DB

원자료 `agri_distribution_data/`(2004~2025년 CSV 22개, 약 4.4GB)를 `db/logistics.duckdb` 하나로 묶은 기록이다.
원자료·DB·중간 파일은 저장소에 올리지 않는다(.gitignore). 대시보드에는 집계 결과 `data/logistics.js`만 배포한다.

## 다시 만들기

```bash
python3 -m venv .venv && .venv/bin/pip install duckdb pandas
.venv/bin/python scripts/clean_raw.py        # cp949 → UTF-8 정제, 원본 줄 번호 부여 → db/clean/ (약 1분)
.venv/bin/python scripts/build_db.py         # 통합 DB → db/logistics.duckdb (약 6분, 0.6GB)
.venv/bin/python scripts/verify_db.py        # 원자료와 대조 → db/verify_report.json (약 3분)
.venv/bin/python scripts/build_logistics.py  # 대시보드 집계 → data/logistics.js (약 4분)
.venv/bin/python scripts/build_od.py         # 기종점 집계 → data/od.js (약 10초)
```

DuckDB의 `encodings` 확장으로 cp949를 직접 읽으면 일부 줄이 깨진다(NUL 문자가 섞인 것처럼 보이지만 원본에는 NUL이 없다).
그래서 Python 코덱으로 엄격하게 해독한 뒤 적재한다.

## 원자료 스키마

22개 파일 모두 쉼표 구분, 따옴표 없음, cp949, CRLF, 같은 22개 컬럼이다. 해독 오류나 필드 수 이상인 줄은 없다.

| 컬럼 | 뜻 | 비고 |
|---|---|---|
| MVMN_CODE | 이동 번호 (8자리) | MVMN_SN과 함께 사실상 고유 키 (2,358만 행 중 4쌍만 겹침) |
| MVMN_SN | 이동 안 일련번호 | 2020년까지 `1.0`, 2021년부터 `1` |
| LOAD_ETPS_TY_CODE / _NM | 출하(상차) 업체 유형 | 농업회사법인·영농조합법인·농협·산지유통인·조합공동사업법인 등 |
| LOAD_ETPS_CTNP_NM / SGGU_NM | 출하 업체 시도·시군구 | 2004~2013년에 빈 값이 있다(최대 6%). 옛 이름과 오기가 섞여 있다 |
| LDCG_YMD | 상차일 `YYYYMMDD` | 파일마다 전년도 상차분이 0.01% 안팎 들어 있다 |
| VRSC_ISTN_CODE / _NM | 신청·정산 기관 | 2012년까지는 지역 농협·연합회(400여 곳), 2013년부터 주관 단체 3~4곳으로 뜻이 바뀐다 |
| UNLOAD_ETPS_TY_CODE / _NM | 도착(하차) 업체 유형 | 대형유통센터·종합유통센터·도매시장·식품가공공장 등 |
| UNLOAD_ETPS_CTNP_NM / SGGU_NM | 도착 업체 시도·시군구 | 주소 일부가 들어간 값이 있다(예: `군위군효령면고곡리`) |

| POOL_CO | 물류기기 풀 운영사 | **2024년부터 컬럼 이름이 `POOL_CO_NM`**. KCP·NPC·SJL·KPN(컨테이너), KPP·AJN(파렛트) |
| LGTC_MCTL_CODE / _NM | 기기 모델 | 예: `NG642(N-4)`, `빨간파렛트(NF-11)` |
| LGTC_MCTL_SE_NM | 기기 구분 | 컨테이너·파렛트·다단식목재상자·상자형파렛트·옥타곤상자 등. 2014년까지 `팰릿`(파렛트의 옛 표기) |
| QYT | 수량(기기 개수) | 2020년까지 `584.0`, 2021년부터 `584`. 0 이하 값과 극단값이 있다 |
| AGRI_CODE / _NM | 품목 | 2004~2005년에는 품종 이름(`사과 후지`, `포도 마스컷`)이 따로 있다. 같은 이름이 시기별로 다른 코드를 쓰기도 한다 |
| ETL_LDG_DT | 적재 시각 | 2004~2020년 파일은 모두 `20210615095711`(일괄 적재) |

파일별 기간: 2004년 파일은 4월부터, 2025년 파일은 11월 30일까지이다. 대시보드는 그래서 2005~2025년의 1~11월만 쓴다.

## 통합 DB 구조 (`db/logistics.duckdb`)

| 객체 | 내용 |
|---|---|
| `movement` | 원본 1행 = 1행 (23,587,668행). 원본 값(`*_raw`)과 정규화한 값을 함께 둔다 |
| `v_clean` | 분석용 보기: `qty_flag = 'ok'`인 행만 |
| `region_alias` | 원본 (시도명, 시군구명) → 시도 코드·시군 키·표시 이름 (출하지·도착지 공용) |
| `crop_alias` | 원본 품목명(199개) → 표준 품목명(160개) |
| `source_file` | 원본 파일 이름·크기·데이터 줄 수 |

`movement`의 주요 컬럼:

- `file_year`, `src_line`: 원본 파일 연도와 줄 번호 (원본과 대조할 때 쓴다)
- `year`, `month`, `load_date`, `unload_date`: **연도는 상차일 기준**. 다음 해 파일에 늦게 등록된 실적도 제 연도로 간다
- `load_sido`, `load_region`: 출하지 시도 코드(`'36'`)·시군 키(`'36|나주시'`). 지역 키는 `data/geo.js`의 현행 시군 단위다
- `dest_sido`, `dest_region`, `dest_place`: 도착지. `dest_place`는 구 단위를 살린 표시 이름(`서울 송파구`)이다
- `equip_type`: `팰릿` → `파렛트`로 통일. `crop`: 품종 이름을 품목으로 묶는다
- `qty_flag`: `ok`, `nonpositive`(0 이하, 주로 2014년 796건), `extreme`(이동 한 건에 2만 개 이상)

정규화 규칙은 `scripts/build_db.py`의 `SIDO_FIX`, `SGG_FIX`, `SIDO_OF_SGG`, `CROP_FIX`에 있다.
- 시도 칸의 시군: 수원시→경기 수원시, 진주시→경남 진주시, 충남당진군송악면→충남 당진시
- 옛 행정구역: 청원군→청주시, 마산·진해시→창원시, 남제주군→서귀포시, 포천·화성·여주·당진군→시
- 줄임 표기: 파주→파주시, 고양→고양시, 달성→달성군

## 검증 결과 (`scripts/verify_db.py`)

원자료를 DuckDB 없이 Python으로 직접 읽어 파일마다 DB와 맞춰 봤고, 22개 파일 모두 일치한다.

- 행 수, QYT·MVMN_SN 합계, 상차일·하차일 합계
- 문자 컬럼 17개의 전체 글자 수
- 기기 구분별 행 수·수량
- 무작위 표본 2,000줄의 22개 값 전부

출하지 지역 매칭률은 2014년 이후 100%이다. 2004~2013년에 남는 0.1~6%는 원본에 출하지가 비어 있는 행이다.
도착 시도 매칭률은 98.8~99.7%이다.

## 수량 이상값

이동 한 건에 2만 개 이상인 행은 기기 종류마다 99.99% 분위수의 3배를 넘는다.
2017년에는 `1,000,000`, `100,000`처럼 딱 떨어지는 값 30건이 그해 컨테이너 수량의 7.0%를 차지한다.
이런 행은 `qty_flag = 'extreme'`으로 표시해 집계에서 뺀다. 다른 해에는 0.1~2% 수준이다.

## 집계 원칙 (대시보드)

사업 예산 규모가 해마다 달라 절대량의 전년 대비 증감은 지역의 변화보다 예산의 변화를 더 많이 반영한다.
그래서 대시보드는 아래 지표를 중심으로 쓰고, 절대량은 참고로만 보여 준다.

- 전국 점유율 = 지역 컨테이너 ÷ 전국 컨테이너. 비교 시점 대비 변화는 %p로 본다
- 상대성장지수 = 점유율(올해) ÷ 점유율(비교 해) × 100. 100보다 크면 전국보다 빠르게 늘었다는 뜻이다. 비교 해 점유율이 0.02% 미만이면 계산하지 않는다
- 구성비(판로, 출하 주체, 풀 운영사, 품목, 도착 시도)와 그 %p 변화
- 특화도(LQ) = 지역 안 품목 비중 ÷ 전국 품목 비중
- 실질 품목 수 = 1 ÷ HHI
- 성수기 집중도 = 이용량이 많은 세 달의 비중
- 지역 간 이동: 시도×시도 이동 행렬, 보내는 곳·받는 곳 상위 지역, 출하·도착 균형 = (출하 − 도착) ÷ (출하 + 도착)

## 기종점 분석 화면 (`od.html`)

지역 동향 화면(`logistics.html`)은 지역 하나를 중심으로 본다. 기종점 분석 화면은 출발 → 도착 쌍을 중심으로 어디서 어디로, 무엇이, 어떤 판로로, 얼마나 멀리 갔는지를 본다.
두 화면은 상단 탭으로 오간다.

- 자료: `data/od.js` (`scripts/build_od.py`). 연도마다 (출발 시군, 도착 시군, 품목, 판로) → 컨테이너 수량을 열 배열로 담는다 (2005~2025년 약 7.4만 행, 1.2MB, gzip 0.3MB)
- 출발·도착은 시도 또는 시군으로 고르고, 품목·판로 조건을 더할 수 있다. 화면에서 그때그때 걸러 계산한다
- 비중의 분모는 전국(품목·판로를 고르면 그 품목·판로)이다. 전국 전체를 볼 때는 다른 시도행 비중을 대신 보인다
- 거리는 시군 중심점(가장 큰 덩어리의 무게중심) 사이 직선거리이고, 컨테이너 수로 가중 평균한다. 경기도만 지도 이름표처럼 중심점을 따로 둔다
- 특화도 = 흐름 안 품목 비중 ÷ 전국 품목 비중. 기종점 순위의 특화 품목은 흐름 안 비중 3% 이상 품목 가운데 특화도가 가장 큰 것
- 실질 도착지(출발지) 수 = 도착(출발) 시군 비중의 HHI 역수
- 상차일과 하차일이 98% 이상 같은 날이라 소요일은 쓰지 않는다
